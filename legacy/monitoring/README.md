# 监控

## 原则：先复用，再自研

brief 的要求是「GPU/硬件监控后续用 Grafana，初期可用**只读 SSH 采集**」，
并且**不要重新实现 EvalScope 已经提供的东西**。本目录因此**不自研监控面板**，
只承载采集侧的设计与落点。

```
monitoring/
├── collectors/   只读采集脚本（未实现）
└── config/       采集配置（未实现）
```

## 阶段划分

| 阶段 | 做法 | 状态 |
|---|---|---|
| 初期 | 只读 SSH 采集，写入 `data/metrics/`，由控制台展示 | 采集逻辑目前**内联在**控制台的固定探针里 |
| 后续 | Grafana 读取 `data/metrics/` | 未安装 |

### 为什么初期采集内联在控制台里

因为**先要证明采集本身是可靠的**。控制台的固定探针（`portal/server.py` 的
`REMOTE_PROBE`）已经跑通并且被验证过，它采集：主机名、内核、uptime、loadavg、
CPU 数、meminfo、磁盘、`nvidia-smi`、systemd 单元状态、监听端口、strata 进程。

把它抽成独立采集器、再拉一套 Grafana，是**在采集还没被证明可靠之前**增加两个
故障面。**抽取的时机是当第二个消费者出现时**，不是现在。

`data/metrics/` 已经是采集的落点（`.gitignore` 已排除，因为它可再生且会持续增长）。

## 已知的采集限制（必须如实呈现，不得平滑掉）

1. **NVML 不可用。** 本机 `nvidia-smi` 因驱动/库版本不匹配失败。实时的 GPU 数据只能
   从 Strata 的 `/v1/status` 取 `machine.gpu`。采集器**不得**在拿不到时回填历史值。
2. **`systemctl is-active strata` 返回 `inactive`，而 `:8080` 在应答。** 这两个单元
   不是该服务的宿主。**端口监听才是事实来源**；采集器同时记录 `ss -ltn` 的监听项和
   `pgrep -af` 到的真实进程。
3. **`df -P / /srv` 在 `/srv` 不是独立挂载点时会打印同一个文件系统两次。** 控制台已按
   挂载点去重，否则面板上会出现一块幽灵磁盘。

## 与 Grafana 的关系

Grafana **未安装**。brief 明确「不为一个首页去引入 Docker」，同样的理由适用于监控：
在确认采集可靠、且确实需要面板之前，不引入容器编排。控制台已经提供了当前的
实时状态、sparkline 与磁盘/内存视图。
